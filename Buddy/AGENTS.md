# Buddy app shell

Read the root `AGENTS.md`, `GLOSSARY.md`, and `docs/adr/` first.

`Spoken replies` is a local saved preference, enabled by default. With it off, the engine shows each line in the notch with its point and annotations, and waits for reading with `waitForReading` before the next. The reply then ends as a spoken one does. The manager owns the cancellable reading timer and rejects stale audio and timer callbacks separately. Muting an active spoken reply stops its audio and keeps its line in the notch. `Latest answer` in settings exposes the full selectable text from existing history. The overlay uses `PointerPose` to aim the triangle toward the target from an 18-point gap, preserving the target coordinates across display origins and edges, and shows a point's label in a pill beside it.

The engine drives the notch with `showNotch(Notch)`, sent only when what it shows changes: `listening(heard:)` while push-to-talk is held, `thinking` once the question is asked, `line` as each line starts or is read, `notice`, `closing` when a reply ends on a line or notice, and `idle` on Esc, an empty transcript or a new text box. `NotchPanel` draws the compact strip in a nonactivating panel on the screen with the cursor, checked every half second. The compact strip is click-through. The open conversation accepts clicks, and only explicit text input takes the keyboard. It wraps the camera housing found from `safeAreaInsets` and the auxiliary top areas, or hangs a stand-in of the same shape from the menu bar. The icon in its right ear swells while listening, turns while thinking and bobs while talking. The strip closes three seconds after `closing`. The manager sends `noticeExpired` four seconds after a notice. The idle icon hides over a full-screen app. `CGWindowListCopyWindowInfo` shows that as the only app with normal on-screen windows on the display, one of which fills it below the camera housing or menu bar. A zoomed window has the same bounds, so the single owner is what tells them apart.

`BuddyApp` runs as a regular macOS Dock app and creates a MainActor `CompanionManager` plus one retained `SettingsWindowController`. The normal settings window opens on launch; closing it keeps shortcuts running, and clicking the Dock icon or choosing Settings reopens it, including after minimization. There is no status item or click-away dismissal. The manager owns the synchronous `BuddyCore` engine, forwards events to it, and performs its effects through the ports in `Ports.swift`: ears (`OnDeviceEars`), mouths (`NeuralVoiceMouth` and `AppleVoiceMouth`), brain, screen (`DisplayCapture`), overlay (`OverlayWindowManager`), notch and its inline text box (`NotchPanel`), store (`HistoryStore`) and agent host (`AgentRunHost`). Put new domain policy in the engine and test it through `handle`, using literal expected effects. Beat parsing, the POINT and annotation tags, and screenshot-to-display mapping live only in BuddyCore. The engine paces a reply line by line: each `speak` effect is one line in a named voice, the mouth reports `lineStarted` and `lineFinished` for it, or `lineFailed` before it starts, and on its start a line's point fires and then each of its `annotate` effects. `hideBuddy` hides the buddy beside the cursor but leaves the annotations drawn, so they stay up after the reply. The engine sends `clearAnnotations` when the next turn starts, on Esc, or when the owner clears history. The overlay keeps its click-through windows while the buddy is shown or any annotation is up, so the buddy flies from one point to the next and back to the cursor before it hides. Each window draws the annotations on its own display, beneath the buddy. A TARGET tag rings its box like RING and makes the reply hold its later lines until the owner clicks inside the box (with a 10-point margin), says "continue" in a new turn, or starts another question. A click during the target's own line counts too. If the target was the reply's last line, the click starts a new turn, "I clicked it.", with a fresh capture, so the next step is read from the changed screen. With no click for a minute, on `clockTick`, the reply ends with a polite line. A TYPE tag sends `type` as its line starts, and only while Accessibility is granted. `PasteInserter` clicks into the field and pastes from a transient, concealed pasteboard item with Command-V, refuses while secure input is on (checked before and after the click and reported as `typingRefused`), and restores the previous clipboard unless something else was copied meanwhile. A new press, Esc or clearing history drops typing that hasn't clicked or pasted yet. The event tap reports left clicks as `clicked` in AppKit coordinates and ignores events marked with `PasteInserter.postedEventMarker`, which are Buddy's own. Agent runs' `show_beats` lines never wait for a target or type. A draw program's marks arrive as one `draw` effect per line. Each window's `DrawMarksView` redraws them with Core Animation beneath the SwiftUI annotations, each of a line's marks drawing on after the one before it from the line's start, and `clearAnnotations` clears them too. Draw programs run in BuddyCore, never in the app. AppKit, Speech, ServiceManagement, event taps, and screen capture stay in this target.

`GlobalPushToTalkShortcutMonitor` forwards physical modifier snapshots (with the event's own timestamp), key presses, clicks and Esc to the engine. Each modifier change includes other keys/buttons currently held and whether secure input permits double-taps. `ShortcutMatcher` in BuddyCore owns held-combo and double-tap matching for the active Talk and Text box slots, retaining `DoubleTap` timing. The defaults are held Control + Option for Talk and double-Control for Text box. `ShortcutSettingsView` edits either trigger kind; the engine rejects conflicts and emits `saveShortcuts`, which the manager persists as `shortcutsV1` data. Rebinding updates the existing matcher immediately and cancels active held Talk, waiting for all modifiers to release before another gesture. Matching emits semantic talk/text-box actions independently of their destination UI. `NotchPanel` is nonactivating. Hovering the notch or its buddy icon continuously for 0.3 seconds opens the current conversation without taking the keyboard. The engine owns that delay, the draft, thread entries and close rules. The open notch stays on its display while the pointer moves. Clicking the inline field or using the Text box trigger takes the keyboard while the owner's app stays frontmost. Leaving closes the thread unless its field is focused or has text. Return sends `textBoxSubmitted`, blur sends `textBoxDismissed`, and Esc closes through `interrupted`. Reply lines enter the thread when speech starts, or when shown with spoken replies off. New conversation ends history through the same summary path as the spoken command. While secure input is on, the tap sees modifier changes but no keys, so it marks double-taps disallowed while held Talk remains available. A typed question then follows the spoken turn's pipeline from the screen capture on. Keystrokes and clicks are logged only when they produce an effect.

The brain is `ClaudeBrain` from BuddyCore: one long-lived `claude -p` stream-json process per conversation, warmed at launch in an empty `Application Support/Buddy/Claude` folder. `TalkConnections` offers Claude/Codex, provider account, and model selection through the owner's existing CLIProxy hub (ADR 0005). With CLIProxy off, its picker is Auto / Claude / Codex instead, saved as `TalkSelection.choice`. The app discovers the hub in Claude settings and reads the existing local proxy keys; only non-secret selection is persisted. Each provider keeps its last account and model, which come back when the owner switches back to it, and choosing the provider already selected changes nothing. `ClaudeLaunch.talk` skips user settings and removes inherited provider variables. Direct mode keeps the CLI login; explicit proxy mode supplies its endpoint/token/model and removes local OAuth. Specific accounts use unique model prefixes; aliases may be added only when unprefixed routing is preserved. Never overwrite an existing prefix, disable another account, or change global routing or CLI profiles. A selection change interrupts the turn and restarts the process, retaining Buddy's recent conversation context. Hub/account failures do not silently fall back. Keep credentials and account identities out of logs and evidence. Do not add telemetry, provider API keys, onboarding requests, or automatic login registration.

With the proxy off, both brains are warm, and Codex's is `CodexBrain` (ADR 0006): one long-lived `codex app-server` process in an empty `Application Support/Buddy/Codex` folder. The engine learns `TalkConnections.setup` through `talkSetupChosen` and picks each turn's provider in `state.provider` with `ProviderRouter`, a pure function in `Headroom.swift`. Headroom is 1 minus the higher of the 5-hour and 7-day utilizations, and a window whose reset has passed counts as unused. Auto stays on the current provider unless the other leads by 15 points, or the current one has reached its limit and the other hasn't. The engine routes at launch, when the owner changes the choice, between turns when usage is reported or a window resets, and as each turn starts, so the provider marked active is where the next turn goes. Unknown usage never shows a lead, and a forced choice always wins. Both brains report usage through `onUsage`, Codex at startup and both during turns, and the engine keeps the latest of each as `state.usage`, which the manager saves under `usageSnapshotsV1` in user defaults. Through CLIProxy the engine records no usage and the chosen provider always answers. Moving a conversation emits `leaveProvider`, and the manager starts the left brain's next conversation fresh and warm, so a turn that comes back to it is primed with the turns it missed. A turn refused for the limit (Claude's `rate_limit` or `billing_error`, Codex's `usageLimitExceeded`) marks that provider's fullest window full and, while nothing of the reply has been heard, is sent again to the other provider. The settings panel shows both providers' headroom and the active one. `CodexLaunch.talk` forces the built-in OpenAI provider, so Codex signs in with the owner's ChatGPT login and never reaches the proxy provider in their Codex config. Each conversation is one ephemeral Codex thread, so `resetProvider` starts a fresh thread on the same process, while Claude's `endConversation` ends its process. `CodexStream` primes each thread's first turn with the recent turns. Each manager owns a UUID directory inside `Buddy Codex screenshots` in the temporary folder. A turn's screenshots are deleted when the turn ends or the process stops, and releasing the manager removes only its own directory. Constructing a manager never empties the shared root or removes another manager's images.

Talk can search the web on either provider. `ClaudeLaunch.talk` offers only Claude Code's `WebSearch` tool and allows it with `--allowedTools`, because a print-mode process with nobody to ask denies it otherwise. `CodexLaunch.talk` sets `web_search="live"`, since Codex's default `cached` mode answers from an index instead of today's pages. Both utility models keep search off. The streams report each search start as `ProviderEvent.searching`: a top-level `WebSearch` tool-use block from Claude, an `item/started` `webSearch` item from Codex. On a search, the engine plays any line written so far at once, except inside a draw program, whose lines end only where the provider breaks them, and when nothing has been said yet it speaks "Let me look that up." The cue is never saved in history. Each talk turn says today's date in the time zone the app gives the engine, so a search about today searches the right day. Claude's search results end with a reminder to cite links, which `TalkInstructions` tells it to ignore because replies are spoken.

A turn that starts with "agent" starts an agent run instead of a reply. A talk reply can also offer one: a line tagged `[RUN:brief]` asks whether to do the brief as an agent run, and the engine holds it in `state.runOffer` once that line starts speaking or is shown. Only a provider reply's line that ends in a question mark offers a run, and a later question in the same reply drops the offer. The next asked turn uses the offer up. A plain yes such as "yes" or "go ahead" starts the run with the brief and the offering turn's screens, without a new capture, and anything else drops it and is asked as usual. Esc, a failed reply, ending the conversation, clearing history or a run's own beats drop it too, and it goes stale ten minutes after it was asked. Several runs can work at once: each turn that starts one adds a card to the end of `state.runs`, the dock's runs in start order, and gets its own provider process, folder, token and time cap. The engine owns each run's state machine (running, paused for a provider switch, needs-owner or taking over, then done, failed, or stopped by the owner, its step cap or its time cap) and the approval policy, and asks for everything else through run effects. `AgentRunHost` performs them. Each run gets a folder in `Application Support/Buddy/Runs/<local time>-<run number>-<UUID>/` holding `brief.md`, the turn's screens, `note.md`, `report.md`, `output/` and `scratch/`. The owner picks Auto / Claude / Codex for new runs in the panel's **Agent runs** card, saved as `runProvider` and sent as `runProviderChosen`. Auto uses `ProviderRouter` at start, independently of talk's provider or account selection; a named provider stays pinned. On an Auto run's limit, `pauseRun` stops its process and tools without cancelling its time cap, and `resumeRun` starts the other direct CLI in the same folder with the original brief, run note and partial report. The run note records the switch and retains that line when progress is updated. Each provider is tried at most once. Pending owner asks stay on the card until answered, with questions paired to answers in the continuation; old approval IDs and screen consent never authorize the replacement. The host rotates the bearer token and rejects callbacks from the stopped process, while late screen callbacks are checked against still-waiting calls. A run keeps its step count and approval mode; its failure notice names its current CLI. The same card picks the approval mode for new runs, Auto, Approve only or YOLO (ADR 0008). It is saved as `runApprovalMode`, and each run keeps the mode it started with. `startRun` carries the mode, and `RunInstructions.system(for:)` gives each mode its own instructions. A Claude run is a `claude -p` process on Opus from `ClaudeLaunch.run`, driven by `RunProcess` and `ClaudeRunStream`. It runs with `--permission-prompt-tool stdio`, so every permission prompt comes to the engine's approval policy. A Codex run is a `codex app-server` process from `CodexLaunch.run`, driven by `RunProcess` and `CodexRunStream` (ADR 0007). It runs from `Application Support/Buddy/Codex run home`, which `CodexLaunch.linkSignIn` fills with links to the owner's `auth.json` and `auth.lock`, so the owner's Codex rules and config never apply. Its thread has full disk access and an untrusted run folder, so every command and patch comes to the same policy, and a denial is steered into the turn with its reason. Each denial lands in the run note. The policy allows reads, operations inside the run folder, read-only commands and read-only AppleScript, and creating new files and folders on the Desktop. It denies `cd`, the shell's own `printf` and tools Buddy doesn't offer, since the run can do those another way. Everything else, such as sending, posting, buying, deleting, changing the owner's files or a command outside the allowed set, waits for the owner: the run moves to needs-owner, Buddy plays its needs-owner cue, and the card highlights and shows Approve and Deny. `RunCues` synthesizes Buddy's own three run sounds: launch when a run starts, needs-owner, and done when a run ends by itself, finished, failed or capped, but not after the owner's Stop. The `ask_owner` tool waits the same way for a question, and so does `begin_takeover`, a request for the screen. The owner clicks a choice, or their next spoken or typed turn becomes the answer instead of going to the provider. With several questions waiting across the dock, the turn answers the one asked first, by the MCP server's call number (`State.questionTakingNextTurn`), and Buddy's reply names that run. Only that question's card invites a spoken answer; the others ask for a click or to wait. The one exception is a continue phrase such as "okay" while a walkthrough is held: it plays the walkthrough, and the question waits for the turn after. Approvals take a click only, so a misheard word can't approve an irreversible action. The MCP config's `timeout` matches the run's time cap, because without it Claude Code abandons an HTTP tool call that waits more than a minute. A run that can't drive an app with AppleScript or the shell can take over the screen. The card shows the run's reason with Allow and Don't Allow, and nothing moves until the owner clicks Allow. A refusal lands in the run note, and without Accessibility the run gets no screen. During the takeover `ScreenTakeover` holds an active event tap at the HID level. It drops the owner's keys, clicks, drags, pointer moves, scrolls, media and Mission Control keys and trackpad gestures, except Esc. Modifier changes pass, so push-to-talk still works, and Buddy's own events pass by `PasteInserter.postedEventMarker`. The `click`, `move`, `scroll`, `type` and `key` tools work only then. They take pixels in the run's latest screenshot, the engine maps them to display points, and `ScreenTakeover` posts them one after another and reports each with `acted`. Typing stops while secure input is on. Taps don't see key events then, so during a takeover the owner's typing reaches the secure field and Esc can't end it, but push-to-talk, which is a modifier change, still can. Esc or push-to-talk gives the owner back the screen at once. So do `end_takeover`, an approval or question that waits for the owner, the run ending, and a tap macOS won't create, which also shows a notice. The run's next screen tool is told why it lost the screen, and the text box's double-tap does nothing during a takeover. While it lasts the buddy stays at the cursor and says it is using the mouse and keyboard and that Esc takes back control. `BuddyPresence.beside` gives that hint priority over a point's label. Talk lines and notices stay in the notch. Only one run holds the screen at a time. Another run's request for it waits on that run's card in needs-owner. Allow on that card while a run holds the screen leaves the request waiting and shows a notice; the owner's clicks are blocked during a takeover anyway, so in practice they answer it after the takeover ends. When the holder gives the screen back with `end_takeover`, Esc or a failed tap, the needs-owner cue plays again if another run is waiting, because the owner couldn't click its card before. Push-to-talk skips it, since the microphone is opening, and a holder that ends plays its done cue instead. One loopback MCP server, started with the first run and stopped at quit, serves Buddy's tools: capture screen, update run note, show beats, ask owner, and begin, use and end a screen takeover. Each run reaches it with its own random bearer token, which is revoked when the run stops. Run events reach the engine on the main queue after the current `send` returns. `DockPanel` in `RunCard.swift` is the dock: one non-activating panel at the right edge of the screen the cursor was on when its first card appeared, holding a card per run in start order. It scrolls when the cards outgrow the screen, and widens by the scroll bar when the system's scroll bars take space (Show scroll bars set to Always, or a mouse attached), so the bar never clips the cards. It comes forward and scrolls to a card that starts needing the owner, and hides when the last card closes. Each card shows the run's number, status, name, request, what it waits for, its run note, its denials and its report, and its Stop control ends that run alone at once. A card in a dock of several keeps its note shorter. A run names itself with the heading its run note starts with, such as `# Rename screenshots`, and `AgentRun.name` falls back to the request until it writes one. Ended cards stay until the owner closes them. A card's Show in Finder control activates Buddy and yields to Finder, because a click on the nonactivating dock leaves Buddy inactive and macOS won't let an inactive app bring Finder forward. When a run ends, the lines and marks it showed leave the screen, after a line still playing finishes. Every talk `TurnRequest`, warm provider or not, carries a dock summary after the profile, or a line saying the dock is empty. For each card it gives the number, the name once the run has named itself, the status, the request, why it failed, the approvals and screen requests it waits for, its run note and, once done, its report. The note, the report and each approval's action are clipped at 500 characters. Waiting questions never appear in it, because such a turn answers the question instead of reaching the provider. Talk answers "how is the agent doing?" from that summary and can't stop or approve a run. Runs read from apps with AppleScript through `osascript`, so the app carries the Apple Events entitlement and its usage text.

The ears are SpeechAnalyzer with a streaming SpeechTranscriber, fully on device. At launch `SpeechAnalyzerTranscriptionProvider` installs the model for the owner's first preferred language through the system's asset inventory, and the panel shows the install. `Locale.current` follows Buddy's English-only interface, so the ears use `Locale.spoken`. Until the model is ready, or when SpeechAnalyzer can't run, upstream's Apple Speech recognizer listens instead. It requires on-device recognition, so it uses the owner's language only when that recognizer runs on device, and US English otherwise. A failed download is tried again on the next push-to-talk. `HeardSpeech` in BuddyCore assembles SpeechTranscriber's results, and the notch shows the heard words beside a waveform that follows the microphone level while push-to-talk is held.

The neural voice is Kokoro 82M with its `af_heart` voice, run on the Neural Engine by FluidAudio. The local `BuddyVoice` package wraps it in `NeuralVoice` and pulls in only FluidAudio's text-to-speech traits. At launch `NeuralVoiceMouth` loads it from `Application Support/Buddy/Voice` only once `NeuralVoice` has found every file it needs there, because FluidAudio fetches a missing lexicon even with its downloads switched off. That check prevents neural-voice downloads from Buddy's process; explicit CLIProxy account discovery is separate. `swift run --package-path BuddyVoice install-voice` downloads the 95 MB of files. Each line is synthesized whole, then `LineAudio` in BuddyCore trims Kokoro's silence and raises its level before `AVAudioPlayer` plays it, so a line's start is reported when its sound starts. A reply picks its voice when its first line is spoken. Until the neural voice is ready, and whenever it is missing or failed to load, the reply speaks with `AppleVoiceMouth`. A line the neural voice can't synthesize is spoken again by the Apple voice, and the rest of that reply stays in the Apple voice. When the neural voice is missing or failed to load, the panel says why. A line it fails while running isn't shown there, because one line Kokoro can't voice, such as an emoji, shouldn't silence it for the session. The first launch after a rebuild compiles the model for the Neural Engine in about 11 seconds. Later launches load it in about 1.5 seconds.

`Logger.turnTiming` records event and effect case names, never transcripts or replies. A `listening with SpeechAnalyzer` or `listening with Apple Speech` line names the ears each turn used, and `speak.neural` or `speak.apple` names the voice of each line. When the neural voice fails a line, `neural voice failed a line` gives only the error's type and case, or its domain and code, because FluidAudio's errors can quote the line. Watch a turn's timing with `/usr/bin/log stream --predicate 'subsystem == "dev.steven.buddy"' --level debug`. Give the full path, because zsh has a builtin named `log`.

`PermissionAdapter` reads current macOS authorization. The legacy `WindowPositionManager` helper exists for the three upstream tests and must never determine the live checklist. Launch at login reads `SMAppService` and changes only after an owner action.

Build and test with the shared `Buddy` scheme. The stable bundle identifier is `dev.steven.buddy`, the deployment target is macOS 26, and the owner's Apple Development signing team is configured in `Buddy.xcodeproj`. Keep the identity stable across rebuilds so permission persistence can be verified.

Run `swift test --package-path BuddyCore` and the `xcodebuild test` command in the root README. Native permission and network checks are listed in `docs/verification/issue-3.md`.

The engine ends a conversation after ten idle minutes or the standalone "new conversation" command. `HistoryStore` atomically saves text-only snapshots to `Application Support/Buddy/history.json`; screenshots are never part of its Codable model. A fresh Claude process or Codex thread receives the summaries of recent earlier conversations, the active conversation's own summary and its last ten turns that summary doesn't cover, while a warm one keeps its own context. Conversation summaries are written by the utility model through `UtilityModel`, a warm provider session that follows the CLI of the provider talk is on, picked when each summary is asked. With Claude Code it is a `claude -p` process from `ClaudeLaunch.utility`: Haiku with the CLI login, or the selected CLIProxy provider and account's small model (`Provider.utilityModels`), keeping the talk model when the account offers or routes none. Proxy mode never falls back to the CLI login. With direct Codex it is a second `codex app-server` whose `CodexThread` has the utility instructions and prefers `gpt-6-luna`. Each answer ends the session's conversation, so the next question gets a fresh Claude process or Codex thread. Switching CLI stops the old utility, failing its question, and the new one retries it. After every event the engine asks for the next summary that is behind, one at a time: a conversation that ended, or the active one once a turn falls out of its last ten. A failed summary waits until the history gains a turn or ends a conversation, or the manager reports `providerChanged` after a selection or CLIProxy connection change. A summary that fails after a `providerChanged` that arrived while it was in flight is retried straight away on the new provider. The first event after launch catches up the last five ended conversations; in proxy mode that first attempt fails until CLIProxy loads, and its `providerChanged` retries it. When a summary lands after the next conversation's process or thread was primed, the following turn resets the provider so it is primed again. Summaries are saved inside `history.json`, so Clear history removes them with it. Clear history resets the provider, cancels active work and removes the file. A load failure preserves the unreadable file and blocks saves until the owner successfully clears it. The manager rejects callbacks from earlier turns with a generation counter.

The profile is the owner's "about you" notes. A talk reply changes it only through line tags: `[REMEMBER:note]` adds a note unless one already matches, and `[FORGET:note]` removes matching notes. Notes match regardless of case, spacing and final punctuation. `BeatParser` reads them anywhere in a line like every other tag, takes the rest of the tag as the note (colons allowed, brackets not), applies them as soon as the line is parsed and still applies them on a line with no words. Agent run beats never edit the profile. Every talk `TurnRequest` carries the profile as its first text block, before any summaries, including on a warm Claude process or Codex thread, and says so when it is empty. `TurnRequest.withoutPriming` keeps it while dropping the priming a warm one already holds. A utility model question (`TurnRequest.question`) carries no profile block. Summaries are written from the turns, though, so a fact the owner said aloud can appear in one; forgetting a note or clearing the profile leaves it there until Clear history. `ProfileStore` atomically writes it as Markdown bullets to `Application Support/Buddy/profile.md`. Like history, an unreadable file is kept and blocks saves until the owner clears the profile in settings. A failed clear blocks saves the same way, so the notes it left behind are never overwritten. Clearing doesn't restart a warm Claude process or Codex thread, so earlier turns' profile blocks stay in its context. The prompt tells Buddy to answer from the profile that came with the current question alone.
